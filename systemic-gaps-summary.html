Out of 175 slots, the honesty pass landed at 117 implemented, 23 partial, 35 persistent — and the 58 non-clean slots cluster into four root patterns, not 58 unique mistakes. That clustering is the finding.

Gap 1 — Compound-effect truncation (the biggest, ~23 slots)

Symptom: a printed card says "do X and Y" (or "X, then sell / influence / travel"), and the code does only X. The drop is silent — the slot still reports success.

  • Board 6 / Slot 4: grants Tools x2 but never places the Lagash raider.
  • Board 8 / Slot 3: grants the resources but skips the sell step.
  • Board 30, the entire row (slots 1–4): each is level-value-only — no influence, no travel, no deploy, no temple. The whole board is half-built.

Root cause: the dropped clause is almost always the interactive one — sell, influence, travel, place. The deterministic head of the effect is easy to auto-resolve; the tail needs a player decision, so it got deferred and never came back. The truncation isn't random — it follows the seam between "compute a value" and "ask the player something."

Fix methodology: treat a printed effect as an ordered list of clauses, not one blob. For each partial, the fix is "implement clause N+1," and clause N+1 is nearly always a decision step that needs a choice descriptor wired in. Batch them by clause-type (all the missing "sells," all the missing "influences") rather than board-by-board — the same helper unblocks a dozen slots.

Prevention: at design-spec time, tag every card effect with its clause count and mark which clauses are interactive. A card with 2 clauses but 1 implemented arm is then a visible mismatch, not a hidden one.

Gap 2 — "Persistent" used as a status that hides un-built work (8 slots)

Symptom: 8 passives are labeled :persistent — which reads like "done, just fires later" — but their dispatch arm is a literal no-op. Boards 5, 10, 14, 21, 24, 30, 31, 33. Board 5/0 is the tell: the code is NO-OP / skip with the comment "complex, would need movement tracking."

Root cause: the status taxonomy collapsed two different things into one label — "this is a passive/triggered effect" (a category) and "this is implemented" (a state). Once a hard passive got parked as :persistent, it looked the same as a working one. The label became a place to hide difficulty.

Fix methodology: split the axis. Category (instant vs. passive) and implementation state (done / partial / stub) are independent — every slot needs both, separately. The 8 stubs then surface immediately as "passive + stub," and "complex, would need movement tracking" becomes a real backlog item instead of a buried comment.

Prevention: never let a single enum carry both "what kind of thing is this" and "is it finished." Any status vocabulary that can absorb an unimplemented effect without flagging it will eventually be used to do exactly that.

Gap 3 — Dual-path divergence (auto-resolve vs. human choice)

Symptom: the same card produces different outcomes depending on who plays it. Board 17 / Slot 1: the auto dispatch flips a raider to point, but bonus-needs-choice? routes the human path as :pick-resource, which grants a resource instead. Bot and human are playing two different cards.

Root cause: there are two code paths for every choice-bearing effect — the human path (apply-bonus-with-choice) and the bot/no-UI fallback (the dispatch arm) — and they were authored separately with no shared source of truth tying both back to the printed intent. They drift the moment one is edited without the other.

Fix methodology: make the printed intent the single spec, and have both paths derive from it — or at minimum add a test that asserts auto-outcome and human-outcome are semantically equivalent for every choice slot. 17/1 is the one I'd eyeball first; there are likely a few more once you assert the invariant.

Prevention: any effect with a human path and an auto path needs a consistency check as a structural rule, not a per-card review. Two independent implementations of one rule will diverge unless something forces them equal.

Gap 4 — Coordinate-system mismatch (spec language vs. code indices)

Symptom: the bug report says "slot 5," the code indexes 0–4, and "slot 5" actually means code index 4. Cheap to reconcile once, expensive every time it's re-encountered — every reader re-derives the off-by-one.

Root cause: player-facing numbering (1–5, or "the 5th slot") was never reconciled with 0-based code indices, so reports and code speak different coordinate systems for the same object.

Fix methodology: pick one canonical addressing scheme and translate at the boundary (UI/report layer), so internal code and specs never disagree. The walkthrough already does this — every Slot 4 entry is tagged as the "slot 5" the bug maps to — which is the translation made explicit.

Prevention: decide the canonical index for any addressable game object once, at design time, and write it into the spec. Off-by-one between spec and code is free to prevent and never stops costing if you don't.

Why this matters for Eridu & Chroma scaffolding

Three of these four gaps are not coding mistakes — they're spec-to-implementation traceability failures. The effect was designed in prose, implemented in code, and nothing structurally tied the two together, so clauses fell out (Gap 1), difficulty got hidden (Gap 2), and parallel implementations drifted (Gap 3). The scaffolding lesson is the same each time:

  • A card's printed text should be a machine-checkable spec, not just flavor. If each effect were authored as a structured list of typed clauses (compute / place / travel / sell / choose), then "is every clause implemented?" and "do the auto and human paths match?" become automatic checks rather than a 175-slot manual audit after the fact.
  • Status vocabulary must never be able to absorb un-built work. Separate "what kind of effect" from "is it finished" from day one.
  • Decide addressing and coordinate conventions before content exists, not after the first bug report exposes the off-by-one.

If Eridu and Chroma both carry a structured effect schema from the start — clauses typed, interactivity flagged, one canonical index, both resolution paths derived from one spec — this entire audit becomes a build-time check that can't silently pass. That's the reusable mechanism worth lifting out of this exercise.
